## Что это за проект

Сервер, который принимает телеметрию с промышленных контроллеров
по MQTT, определяет аварийные состояния и рассылает уведомления
потребителям по HTTP-вебхукам.

Первый подключаемый контроллер — **Licos**, работает по открытому
MQTT publish. Схема его топиков **ещё не разведана** — это первая
задача (`mosquitto_sub -h <ip> -t "#" -v`).

## Ключевое архитектурное решение

Единственный транспорт наружу — **вебхук (HTTP POST)**.

Мы сознательно НЕ делаем push на мобильные (FCM/APNs) и НЕ делаем
WebSocket. У всех потребителей — мобильного приложения, веб-приложения —
есть собственные бэкенды. Наш сервер доставляет событие до их сервера,
а как оно превратится в уведомление на конкретном экране — их зона
ответственности.

Это даёт независимость от платформ: сервер умеет делать HTTP POST,
и всё. Новый потребитель подключается регистрацией URL.

**Не предлагай добавить FCM, APNs или WebSocket.** Решение принято
осознанно. Если увидишь причину его пересмотреть — сначала обсуди.

## Поток данных

```
Контроллеры ──MQTT──▶ Ingest ──▶ Engine ──▶ Шина ──▶ Webhook-адаптер
                                (правила,                    │
                              дедупликация)                  ▼
                                                    Серверы потребителей
```

Ядро формирует нормализованное событие и кладёт в шину. Ядро не знает
о существовании конкретных получателей.

## Контракт: нормализованное событие

Главный контракт системы. **Менять его нельзя без согласования** —
на него уже ориентируется команда мобильного приложения.

```json
{
  "id": "a3f2c81b9e...",
  "ts": "2026-07-29T14:23:11+00:00",
  "source": "licos-01",
  "type": "alarm.raised",
  "severity": "critical",
  "code": "TEMP_OUT_OF_RANGE",
  "title": "Температура вне нормы",
  "message": "Текущее значение: 85.2 °C\nДопустимо: от -40.0 до 80.0",
  "value": 85.2,
  "topic": "licos/sensor/temperature",
  "acknowledged": false
}
```

- `type`: `alarm.raised` | `alarm.cleared` | `info`
- `severity`: `critical` | `warning` | `info`
- `id`: потребители отбрасывают по нему дубли при повторной доставке

## Требования к надёжности

Вебхук — единственный путь наружу, поэтому:

1. **Дедупликация аварий.** Контроллер публикует состояние циклически.
   Событие отправляется ТОЛЬКО при переходе норма → авария
   и авария → норма. Пока авария висит — тишина.

2. **Очередь доставки с повторами.** Событие не доставлено, пока
   не получен HTTP 2xx. Иначе повтор с экспоненциальной задержкой
   (5 с → 30 с → 2 мин → 10 мин). Очередь переживает перезапуск сервера.

3. **Watchdog.** Молчание контроллера дольше заданного времени — тоже
   авария (`LINK_LOST`). Умершее устройство ничего не опубликует,
   и тишину нельзя принимать за «всё хорошо».

4. **REST для досинхронизации.** Push не даёт гарантий. Потребитель
   должен уметь спросить, что пропустил: `GET /api/events?since=<ts>`
   и `GET /api/alarms/active`. Схема: push для скорости, pull
   для гарантии.

## Стек

- Python 3.12
- FastAPI + uvicorn — REST API и автодокументация на `/docs`
- paho-mqtt 2.x — приём из MQTT
- httpx — асинхронные исходящие HTTP-запросы
- SQLite на старте, PostgreSQL в продакшене
- Docker для развёртывания

Прежде чем предлагать новую зависимость — объясни, почему без неё
не обойтись.
